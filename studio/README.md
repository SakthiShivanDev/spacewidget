# SpaceWidget Studio

A separately deployable visual builder and API server for the SpaceWidget Flutter runtime. This service owns screen/component authoring, database bindings, API keys, user accounts, draft/published versions and action endpoints. It is independent of the Flutter-only core package.

## Run locally

Requires **Node.js 24+** (see `.nvmrc`). Use Node 24 for installation, builds and tests; the server uses PostgreSQL for all persistent data. Your existing global Node installation is not modified by this repository.

```sh
cd studio
npm ci
npm run configure
# Set STUDIO_DATABASE_URL in .env, or use installed local PostgreSQL 16 binaries:
npm run db:local
npm run build
npm start
```

Open **http://localhost:4100**. On first run, enter the `STUDIO_SETUP_TOKEN` from the private `.env` generated by `configure`, then choose your owner email and password. That setup endpoint closes after the first owner exists. Use “Invite a builder” in the left rail to provision additional isolated builder accounts. Invitations expire after 72 hours and are single-use. App users and Studio builder accounts are separate.

Create an app to get Main, Profile and Sign in screens, a reusable welcome component, managed demo tables and a user-owned profile update action. The managed app tables, Studio accounts, definitions, sessions, commerce and notifications all persist in PostgreSQL. Use `STUDIO_DATABASE_URL` (or hosting-platform `DATABASE_URL`) and preserve `STUDIO_MASTER_KEY`. Remote connections verify TLS by default. Managed tables are isolated per app; external data connectors can use a separate PostgreSQL database.

For live frontend development, run `npm run web` in a second terminal and open http://localhost:5173. The Vite proxy connects to the API on port 4100. Use the same hostname in both URLs for cookie behaviour.

## Design screens and components

- Screens/Components: use the layer tree, insert palette, property inspector, JSON editor, duplicate/delete, sibling reorder and undo/redo. Drag palette widgets onto a parent or click to insert them. Layout follows Flutter rows, columns and containers; this is a structural app editor, rather than a free-position vector drawing tool.
- All 120 core widget names are available through palette search, with optional platform and auth widgets. Appearance covers common properties, Content connects fields, and Interactions configures events. Technical properties provides the full widget schema and JSON editing. Platform SDK widgets still require their consuming application's setup.
- Create a component from a selected widget or start a component separately. Use `{{props.title}}` in its tree, define defaults, then pass instance `values`. Components may contain components. Publication rejects missing references/cycles; expansion has depth and size limits. Screen responses contain expanded trees, so components require no additional network request. Components are captured in immutable published releases.
- The canvas uses **Flutter only**. In **Edit** mode, click rendered widgets to select their source layer, drag widgets from Insert, move layers between layouts, and resize widgets that support width/height using the bottom-right handle. Double-click the preview to enable taps, scrolling, forms and navigation between unsaved draft screens. Select returns to editing; Reset clears preview state. Components and repeated items map selection back to their authoring instance/template.
- Resize the Layers and Properties panels by dragging their divider (or focus a divider and use arrow keys). Collapse layer groups, toggle either panel, scroll the workspace, zoom, fit, and choose phone/tablet/desktop/custom viewport sizes. The artboard dimensions are the actual Flutter viewport.
- Every insertion picker searches friendly widget names, runtime type names and categories, including reusable components. Use arrow keys and Enter in the picker. Form fields and constrained slots recommend the supported types. Components that would introduce a cycle are excluded.
- Preview sample data is separate from runtime data; use Content → Preview data or the Content inspector’s Load records to read an authorized sample from the unsaved draft query. Run navigation requests draft screen JSON through the authenticated builder session. Database writes, authentication/provider operations and other service actions still require testing in the connected app; the canvas does not provide a runtime app credential.
- Drafts autosave after a short pause and keep a browser recovery copy while unsaved. Save remains available explicitly. Publish waits for pending saves, validates database resources, then creates an immutable version. Draft changes do not affect connected apps. Releases can reactivate earlier versions without overwriting the draft. Concurrent saves use revision checks and reject stale edits.

### Compare the draft with your Flutter app

The **Draft / Published app** switch above the canvas makes the preview source explicit. Draft renders unsaved edits. Published app renders the currently active immutable release in a read-only canvas; it never replaces your draft. The header shows the saved draft revision and live release version separately. A screen added after the active release exists only in Draft until published.

Select **Sample content** for authored examples or **Live content** to run the selected version’s real data queries. Published comparison starts with database records and uses the same expanded widget tree and public query results as the runtime API. Private sources need an explicitly chosen app user in the Content inspector; the canvas reports sources that could not load private records. Comparing different records, release versions or logical viewport widths can change the visible layout. Studio and the runtime share `buildSpaceTheme` for the same Material colors, fonts and brightness defaults.

Publish the draft when ready, then reload the connected app so it fetches the new release. Match the app window size to the canvas’s logical dimensions when comparing wrapping and responsive grids. Canvas zoom scales the editor view; it does not change the Flutter viewport. Writes and provider-dependent operations still need the connected app.

### Connect data without writing bindings

The right sidebar has **Design**, **Data**, **Actions** and **Advanced** tabs. Design shows essential layout, typography, fill, stroke and content controls, including named font weights and editable spacing sides. Advanced retains every widget property and its JSON editor. Actions contains event configuration. The color picker translates Flutter ARGB and named colors into the correct RGB swatch and keeps explicit alpha when changing a color.

1. In Data, choose **Add data source**. The guided setup asks for the database/table, a collection or single record, the fields your design needs, and access/filter rules. Filters use labels such as “contains” and “is less than.” Owner-scoped data automatically makes the screen require sign-in.
2. For a collection, choose **Build list or grid**. Pick which field supplies the item title and supporting text, then add the design to the screen. This creates a repeat widget and one editable template. Existing layouts remain in place.
3. Select the repeated collection → **Data** to change its collection, list/grid layout, columns and gap. Choose **Load records** to preview real content without saving the draft, then **Edit item design**.
4. Select a text or image within that design and open **Data**. Pick a **Current item** field to connect it. The field picker shows sample values and searches friendly names; a collection is offered only to collection properties, not as text. Single-record sources can connect directly to a text or image layer.

**Connect data** beside content properties opens this same picker. Connecting imported literal text enables runtime binding automatically; disconnecting removes that property binding. Component item designers can use fields from the collection supplied by a screen instance. For Product grid instances, **Content → Map card content** provides field dropdowns for name, category, price and image while Design retains visual settings such as currency, columns and spacing. Individual field mappings and collection bindings remain in Technical properties for developers.

Data-preview reads accept the unsaved definition and do not save, publish or mutate application records. Choose a test app user before loading private data. The app still supplies actual request parameters and verified authentication when fetching production data.

### Import a Figma design

Use **Import Figma** in the editor toolbar to download the companion plugin ZIP. Extract it, then in **Figma desktop → Plugins → Development → Import plugin from manifest…**, choose `manifest.json`. This is a one-time setup; no Figma API token or Studio credentials are needed inside the plugin. The companion plugin runs offline and only reads the selected design.

1. Select a Figma frame and run **SpaceWidget · Copy to Studio**.
2. Click **Export selection → Copy for Studio**.
3. Return to the Studio editor and press **Ctrl/Cmd+V** outside a text field, or open **Import Figma** and paste into the export box. Download/upload the JSON if clipboard permissions are unavailable.
4. Review the frame, import mode and destination, then choose **Import design**. The default creates a new screen and opens the Flutter viewport at the original frame size. You can also create a reusable component, insert into the selected layout, or explicitly replace the current layout. Undo restores the draft; Save and Publish remain explicit.

**Editable layers** maps supported text, solid rectangles and frames to named Flutter widgets with measured positions and sizes. Complex vectors, images, gradients, masks, effects and advanced text are preserved as PNG layers. Text remains literal initially (including `{{...}}` design copy); turn off its `literal` property when adding runtime bindings. Fonts must be available in the consuming Flutter app. Text metrics and some Flutter rendering can differ from Figma. Imported positions are fixed at the copied frame size; they do not automatically become responsive Row/Column layouts or functional forms.

**Visual snapshot** preserves the exported PNG appearance as one image. Its individual layers cannot be edited or bound to data. Studio also accepts PNG files and clipboard PNG images directly. Normal Figma copy/link data opens setup guidance; it is not treated as an editable export. The image scales with its imported bounds, so scaling can affect sharpness.

The review shows the Figma reference image, font requirements and export notes. Import one of up to 10 exported frames at a time. Exports are limited to 1.5 MB, 500 layers, 24 nested levels, and 16 megapixels per image. Converted layouts must also fit Studio’s rendering depth/size budget; imports that exceed it are rejected before changing the draft. Prefer smaller selections or Visual snapshot when a limit is exceeded. Assets are embedded in the screen JSON, so they render without a Figma account or external image server. Imports preserve existing data settings and actions; configure API bindings, authentication and interactive actions in the inspector after import.

The plugin sources and installation notes live in [figma-plugin](figma-plugin/README.txt). Automated tests cover conversion, plugin sandbox execution with API stubs, ZIP delivery, clipboard review and actual Flutter rendering. Installation and clipboard behavior inside a real Figma desktop session require a manual check.

### Customize widgets

Select a widget on the Flutter canvas or in **Layers**. Its inspector exposes the Flutter properties for all 133 installed runtime type names, including aliases and optional adapters. Values imported through `props`, top-level properties or legacy `style` remain editable with the same precedence as Flutter.

- **Forms:** select a form, choose **Field type**, then **Add field**. Click a field in the form's child list to edit its label, name, binding, validation and options. New field names are unique; set them to your server action's expected field names when connecting a manually built form. Forms that use a child layout add fields inside that layout.
- **Bottom navigation:** insert `bottomNavigationBar` or `navigationBar`, then use **Add navigation item**. Edit each label/icon and select its destination screen. Items can be reordered or removed; Material navigation retains at least two items. New navigation widgets use an independent state binding.
- **Lists and structured values:** dropdown/radio/multiselect options, stepper steps, table columns/rows, timeline entries and map markers have add/edit/remove controls. Option values retain their text, number or boolean type. JSON controls remain available for custom records and bindings.
- **Layout and children:** add, select, replace or remove widget slots directly. Tabs keep controller length, labels and pages synchronized. Slivers, flex children, positioned content and page views receive the Flutter parent/constraints needed when inserted into an ordinary scrolling screen. Edit the generated wrapper in Layers to change its bounds.
- **Appearance and events:** use each widget's actual supported properties. Reset removes shadowing values from all property layers. Numeric/color/structured controls validate before applying; structured edits use **Apply**. Bindings such as `{{user.name}}` remain strings in JSON until resolved by the runtime. The binding picker lets you choose the target property explicitly.
- **Authentication:** auth form titles, subtitles, field labels, submit text and success actions are configurable. Switching an auth form into another mode retains that mode's default copy unless separately authored.

Design sections collapse independently; use Actions for events and Advanced for the complete runtime property list. Component defaults and instance overrides have typed controls; JSON remains available for advanced edits. Keyboard shortcuts include Ctrl/Cmd+S, undo/redo, Ctrl/Cmd+D, Delete, Escape, V (Select) and H/Space (Hand). Flutter layout constraints remain authoritative; canvas tools do not convert Row/Column layouts into free positioning.

Preview updates keep the controller, input values and scroll state when the screen/component scope is unchanged. Switching scope or using Reset starts fresh state. Updates and render acknowledgements carry revision IDs, and superseded HTTP requests are cancelled. Render errors appear under Preview diagnostics. A missing preview build shows a recovery message instead of recursively loading Studio inside the iframe. Validate provider-dependent widgets in the consuming app.

### Product grid component

The reusable [Product grid definition](components/product-grid.json) binds to the screen's `products` list. It uses two columns below 600px, three below 1024px and four on wider layouts. Cards show a square image, category, a two-line product name and price. Missing image URLs use a placeholder; empty results show “No products found.”

In Components → Product grid → Edit default properties, customize `currency`, `columns`, `tabletColumns`, `desktopColumns`, `spacing`, `cardAspectRatio`, `emptyText` and the source field names (`nameField`, `categoryField`, `priceField`, `imageField`). The default image field is `image_url`; include it in the data source when your table provides it. Existing demo tables have no image column and use the placeholder.

`onProductTap` is optional. For example, set it to `{"type":"navigate","source":"/runtime/screens/product-details","query":{"id":"{{item.id}}"}}` after creating that destination screen. Component instances can override defaults through their `values`.

Server operators can install it into a locally stored app draft from `studio`:

```sh
node scripts/add-product-grid.mjs --app-id YOUR_APP_ID --screen main
```

This requires an existing `products` list source. It backs up the draft, replaces a single existing product repeat (or appends the component), and increments the draft revision with a conflict check. It preserves the published release; review and publish through Studio. Additional instances are available under Insert → Your components.

## Connect a database

Content → Connect database accepts a PostgreSQL URL, TLS verification setting and optional CA certificate. Credentials are encrypted with AES-256-GCM using `STUDIO_MASTER_KEY`; API responses never return the stored credentials. Keep this master key with your backups. Production connectors require an explicit `STUDIO_DB_HOSTS` allowlist; URLs with connection query options are rejected. Configure TLS separately and use a database role limited to the intended public-schema tables.

Choose a screen data source: connection, table, selected columns, fixed/request/user filters, ordering, page size, and single/list mode. Scope `user` automatically adds an immutable ownership condition using the verified app user's ID. A screen containing a user-scoped query must require authentication. Public data sources are intentionally public to holders of the app's publishable key; select their fields accordingly. Tables need a stable `id` column; user-scoped resources also need the configured owner column.

Single records bind as `{{user.name}}`. Lists bind as `{{products}}`; their page metadata is available as `{{productsPage.nextCursor}}`. Initial data is embedded with the screen. For subsequent pages, use `paginatedList` with `source: '/runtime/data/main/products'`, `initialItems: '{{products}}'` and `nextCursor: '{{productsPage.nextCursor}}'`.

Values are parameterized; table/column identifiers are checked against introspection. Searches escape wildcard characters. Cursors are signed and tied to the app, release, user and query. Screen queries with identical definitions reuse one result within that response. There is no cross-user query cache.

Create server actions with explicit editable fields. Every mutation requires a verified user and ownership column. Inserts set IDs and ownership on the server; updates/deletes add mandatory ownership conditions. Additional filters can match a submitted record ID. Submitted ownership/ID fields cannot override these rules. “Add form to screen” creates inputs and a submit button using the published action endpoint. Numeric form strings are validated and converted according to the action definition. For external PostgreSQL, the builder must create the application's tables/constraints; Studio does not run arbitrary DDL or create them automatically.

## Connect Flutter

Use the local `spacewidget_adapters` package, then:

```dart
import 'package:flutter/material.dart';
import 'package:spacewidget_adapters/spacewidget_adapters.dart';

void main() => runApp(const SpaceHostedApp(
  baseUrl: 'https://studio.example.com',
  apiKey: 'YOUR_PUBLISHABLE_RUNTIME_KEY',
));
```

Create the key in Studio → App settings → Connect app. The server resolves the app and initial published screen from that key. Keys are stored as hashes, displayed once, and can be rotated/revoked. `baseUrl` is the server origin; runtime routes live at `/runtime`. Loopback HTTP is accepted for development; other HTTP origins require explicit `SpaceClient(allowInsecureHttp: true)`. Normal deployed apps use HTTPS.

For configured media/maps, custom operations/streams, or session storage, create `SpaceClient` and pass `SpaceHostedApp.client(client: client)`; the host owns and disposes that client. `client.services`, `client.widgets`, and `client.controller` also work with existing `SpaceApp` integrations. Credentials are per-client; there is no global singleton.

Public runtime keys identify apps and do not grant builder/database administration. Private screens/actions additionally use the app user's bearer token. The app key cannot select another app's tables or user sessions.

## Authentication

Built-in runtime auth supports email/password registration/login, 15-minute signed access tokens, rotating 30-day refresh sessions, restoration, logout revocation, one-use password reset codes, and email verification codes. Refresh-token replay revokes that session family. Codes expire after 10 minutes and allow up to five attempts. This is email verification, not SMS OTP or multi-factor authentication.

The Flutter companion provides `loginForm`, `signUpForm`, `forgotPasswordForm`, `resetPasswordForm`, `otpForm`, and `authGate`. Private-screen challenges render sign-in UI; successful sign-in refreshes the requested screen. Logout resets the app navigator and removes local private screen state. Tokens use `SpaceSecureSessionStore` by default and never enter widget state or action result bindings. `SpaceMemorySessionStore` is an explicit non-persistent option for demos/tests. Native secure-storage setup and HTTPS/secure-context requirements apply; see the plugin's platform documentation.

Expired sessions share one refresh across concurrent requests. GET requests can retry once after refresh; mutations are not automatically replayed. Logout clears local state immediately; if the network is unavailable the server revocation cannot be confirmed, so the outstanding server session remains subject to expiry/revocation.

Set `SMTP_URL` and `MAIL_FROM` for actual reset/verification delivery. Production returns an unavailable-service error if SMTP is missing. Development without SMTP uses an encrypted owner-visible outbox in Authentication. There are no default user credentials, public signup for Studio builders, OAuth/social providers, or SMS providers. The server owner can invite builders; each builder's apps remain isolated. Shared-project collaboration is a separate future capability. A server operator can recover a builder account with `npm run admin:reset`; the script prompts for a hidden password and revokes existing Studio sessions.

## Deploy on your server

Docker/Caddy configuration is included. It has not been deployed to an external host by this coding session. Configure DNS for your domain, then set private environment values in `.env`:

```text
STUDIO_HOSTNAME=studio.example.com
STUDIO_MASTER_KEY=<preserve the generated 64-character hex key>
STUDIO_SETUP_TOKEN=<preserve the generated setup token>
STUDIO_DATABASE_URL=postgresql://studio:password@your-postgres-host.example.com/spacewidget
STUDIO_DB_HOSTS=your-postgres-host.example.com
SMTP_URL=<your SMTP connection>
MAIL_FROM=SpaceWidget <noreply@example.com>
```

```sh
npm run preview:build  # required for the authoring canvas
# Requires Docker Compose on your server:
docker compose up --build -d
```

Caddy terminates HTTPS and proxies to Studio; only the proxy publishes ports. Compose sets `STUDIO_TRUSTED_PROXIES=loopback,uniquelocal` because only Caddy exposes a public port and its upstream connection uses the private container network. This lets rate limits use the forwarded client address. You can narrow this list to your proxy IPs/CIDRs. Other deployments default to trusting no forwarded addresses; configure the actual trusted proxy addresses and restrict direct access to the app port. Use a persistent PostgreSQL service and back it up with `pg_dump` or your provider’s consistent backup facility. Preserve the encryption key separately. The local `db:local` helper is for development; its cluster lives under `data/postgres`. Published versions still depend on current database schemas; rolling back screen JSON does not roll back your database.

## Validate

```sh
npm test
npm run build
npm run test:browser
npm run test:client:web  # requires Flutter and Chrome
```

Server tests cover draft isolation, release rollback, component validation, builder isolation/CSRF, key rotation/revocation, signed cursors, SQL search, private writes, session refresh/replay, recovery and verification. The PostgreSQL integration creates a temporary loopback PostgreSQL 16 cluster when the binaries are available to a non-root user; otherwise supply `STUDIO_TEST_POSTGRES_URL` for an isolated test database. It creates/drops only its uniquely named test table. Catalog tests additionally check every installed widget definition and property editor; the preview package runs 120 actual Flutter default/layout cases. Browser tests use Chrome (`CHROME_BIN` overrides `/usr/bin/google-chrome`) and exercise editing, reusable components, database bindings, publishing, runtime keys and the Flutter iframe.

The web-client check starts an isolated API and runs the real Dart/Dio client in Chrome from another origin, covering app-key requests, JSON registration, bearer-token reads and readable authentication errors. Set `FLUTTER_BIN` and `CHROME_BIN` if needed.

From `packages/spacewidget_adapters`, `flutter test` also covers the hosted SDK. Its real-server integration requires Node 24 and the Studio dependencies installed; use `STUDIO_NODE_BIN` when that Node binary is not on PATH. Existing core and industry demos remain independent.

### Editing layers and testing interactions

Duplicate a selected layer with the inspector button or Ctrl/Cmd+D. A duplicate in a single-child slot stays inside its parent by introducing a Column. Wrap with… and Replace widget… provide searchable choices. Replacements preserve the layer ID, compatible properties and existing children; conversions that would discard child widgets are rejected. Icon → IconButton preserves the icon, size and color; choose its action in Actions.

Drag layers between parents or drop palette widgets directly into Layers or the Flutter canvas. Top/bottom drop positions insert before/after; the middle inserts inside a container. Invalid destinations show a message. Structural edits support Undo/Redo.

The canvas has Select, Insert and Reset controls. Double-click the Flutter preview to use buttons, forms, navigation and pull-to-refresh. Click Select (or select a layer in Layers) to resume editing. There are no Run or Pan controls. Wheel scrolling and zoom remain available. Preview refresh reloads the selected draft/published screen and its configured data sources; database writes still require running the connected app.

### App theme and preview consistency

Choose the theme when creating an app, or use **Theme** in the top bar later. Theme settings belong to the draft and publish together with screens. The hosted Flutter app consumes this server configuration automatically; it needs no separate Dart color configuration. Use Published app with Database records to compare the live release. Match device dimensions and light/dark appearance when comparing platforms.

Theme settings include seed and exact primary/secondary colors, scaffold background, surface/error colors, text-on-color overrides, light/dark/system appearance, body font size, common component corners and custom TTF/OTF uploads. Dark colors generate independently unless explicitly overridden. Uploaded font metadata supplies weights/styles; include every weight/style the app uses. Uploads support 12 files, 2 MB each and approximately 4 MB combined. Fonts are embedded in the versioned theme and loaded by both Studio and Flutter. Uploaded families are namespaced by their contents so separate apps can reuse a family name safely.

Color properties offer **Inherit from app theme**, theme roles such as Primary/Surface, and Custom color. Theme references serialize as `@theme.primary`, `@theme.onPrimary`, `@theme.secondary`, `@theme.onSecondary`, `@theme.surface`, `@theme.onSurface`, `@theme.background`, `@theme.error` and `@theme.onError`. Explicit colors and nested Theme widgets override the global theme. A bare SpaceWidget embedded in an existing MaterialApp inherits that host theme: use SpaceHostedApp for server-controlled app theming.

For images, supply a direct image URL with browser CORS access or upload a PNG/JPEG/WebP/GIF under 4 MB. Uploaded images travel with the screen. Bundled assets must exist in the consuming Flutter app. Image failures are reported in preview issues. The Studio browser policy permits HTTPS image fetches (and local HTTP development); an external image host must still permit CORS.

## PostgreSQL migration and new platform features

Existing SQLite installations: stop Studio, set `STUDIO_DATABASE_URL` to an **empty** PostgreSQL schema, preserve the original `STUDIO_MASTER_KEY`, then run `npm run db:import-sqlite -- path/to/studio.sqlite`. The read-only utility saves a consistent SQLite backup, imports dependency-ordered tables in one PostgreSQL transaction and compares every table’s row count and SHA-256 checksum before committing. It refuses a nonempty target. SQLite is never loaded by the Studio server. Keep the snapshot and migration report in `data/backups`; remove the old `STUDIO_DB` environment setting after successful migration.

- **Content → API connections:** save authenticated external REST endpoints, test GET responses as a public visitor or selected app user, then connect them to a screen under a readable source name. HTTP credentials stay encrypted on the server. Only approved hosts are contacted, redirects are rejected, responses are capped at 1 MB and private calls receive the authenticated user ID from the server. Public endpoints are read-only. Saved credentials are retained when omitted from an update; replacing credentials requires new header values.
- **AI design:** save your OpenAI, Gemini or Claude key and an available structured-output model ID. Keys belong to the Studio builder account and are encrypted. Generate a new screen or component, review the proposal and Apply it to the draft. Apply supports Undo and never publishes. The provider receives the prompt, widget catalog and theme; it does not receive database records, saved connector credentials or app tokens. Provider errors are sanitized. Generated proposals cannot contain executable actions or network resources; wire those after reviewing the design. Model access and billing must be configured in your provider account.
- **Integrations:** check Google/Apple sign-in, Stripe/Razorpay and Firebase readiness. Send a notification to one app user after reviewing it, with a published screen destination. Only that user can resolve its notification ID. Firebase delivers opaque IDs to registered active sessions; logout revokes device associations. General notifications work without an order.
- **External apps:** save named HTTPS/email/telephone/custom-scheme destinations, then use `openExternalApp` with `{name: "Support"}` in a widget integration action. Custom schemes must also be allowed by `SpacePlatform(allowedAppSchemes: {...})` and configured in Android/iOS. Regular `openUrl` and checkout continue to require HTTPS. Authenticated REST providers are connected in Content → API connections.
- **Custom code:** backend JavaScript modules return JSON from `(context) => result`. Test a draft, save and explicitly Enable its saved version. Signed-in app users call `POST /runtime/functions/<id>`; their identity is supplied by the server. Editing a draft does not change the enabled version. QuickJS runs in a separate worker with a 16 MB heap, 500 ms execution deadline and an outer wall-clock timeout. It exposes no filesystem, environment, Node APIs, network or async functions. Use saved HTTP services for network integrations and guided data actions for owned database writes. Dart modules are authored/downloaded in Studio, compiled into the Flutter host and registered through `spaceCustomWidgets`. They are **not dynamically executed from server text**. Add a `customWidget` layer with the registered name. Rebuild both the host and Studio’s preview when changing compiled Dart; an unregistered builder shows a clear placeholder.

See [platform setup](../docs/platform-setup.md) for provider environment variables and test limits.
